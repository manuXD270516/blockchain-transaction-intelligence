# M2 — Canonical transaction evidence v1

Función pura `normalizeInvestigation(Investigation)` sin IO, red, reloj ni mutación. Devuelve bundle deep-frozen v1, mode/chain_id, snapshot, acquisition_status, execution_status, coverage, transaction/receipt/block nullable, fees, raw completo, evidence DAG, warnings y bundle_id. IDs SHA-256 sobre JSON ordenado por claves (arrays mantienen orden; no normalización Unicode), schema y contexto. Misma entrada→mismos bytes/IDs. Capturas live con distintos timestamps/request ids son entradas diferentes y pueden cambiar ids; no prometer identidad entre capturas distintas.

## Datos canónicos

Cada entidad tiene schema_version, id chain-qualified, raw_evidence_id, normalization_evidence_id y fields. Transaction: hash, from/to, nonce, value_wei (valor declarado, no transferencia efectiva), input, type decimal o null, gas_limit, gas_price_wei, max_fee_per_gas_wei, max_priority_fee_per_gas_wei, max_fee_per_blob_gas_wei, block_hash, block_number, transaction_index, is_creation. Receipt: transaction_hash, block_hash/number/index, status, gas_used, cumulative_gas_used, effective_gas_price_wei, contract_address, blob_gas_used/price. Block: hash, parent_hash, number, timestamp_unix_seconds, gas_used/limit, base_fee_per_gas_wei, transaction_hashes. Log: block/tx/log ids, emisor, topics, data, removed=false, cantidades de índices decimales; sin ABI ni interpretación de eventos.

Cantidades raw deben ser hex QUANTITY canónico de hasta 256 bits. Convertir con BigInt, nunca Number; campos opcionales ausentes/null→null. Campo presente inválido→INVALID_NORMALIZATION_INPUT, no null silencioso. Hash/dirección lowercase estrictos; otros formats requieren cambio explícito. `to=null` indica creación; no inventar contract_address si falta o si falló. Campos desconocidos quedan en raw aunque no tengan campo canónico; tipo desconocido se conserva decimal y genera UNKNOWN_TRANSACTION_TYPE.

IDs: transaction incluye chain/tx/block-or-pending; receipt y logs incluyen snapshot; block incluye chain/hash. block_hash desconocido en pending permanece null. Revalidar tx/receipt/block, membership, chainId si existe, snapshot e índices/logs contra sus padres. No aceptar receipt de otra tx ni logs duplicados/removed. Receipt ausente→pending sólo con tx no incluida, otherwise unknown; not_found requiere todos raw null y snapshot null. Recalcular estados y exigir coincidencia con entrada M1; impedir elevar partial a ok por datos contradictorios. Cobertura de M2 se refiere sólo a estos objetos, no a trazas ni documentación.

## Evidencia

Validar SHA-256 contra bytes UTF-8 de cada evidencia M1, envelope/id y método/params para fuentes RPC; provider/source kind debe corresponder al modo. Encontrar evidencia cuyo result coincide con cada raw usando comparación canónica y hash del tx/bloque solicitado. FixtureAdapter entrega JSON raw reserializado: nombrar explícitamente `fixture_materialized`, conservar hashes de manifest/artifact de params como referencias upstream, sin afirmar que son bytes originales del archivo. Ausencia de fuente coincidente→MISSING_EVIDENCE; SHA alterado→EVIDENCE_INTEGRITY_ERROR.

Raw nodes conservan source method/provider/captured_at/request_id/params y raw_utf8; locator raíz de payload (`/result` para RPC, raíz para fixture). Derived nodes incluyen transformation/version, parent_evidence_ids y field_sources (JSON Pointers de inputs) + value canónico. El builder sólo enlaza padres ya existentes, sin ciclos; no recibe IDs del modelo. Raw desconocido permanece accesible. Validar también evidencia de null cuando fuente existe; not_found fixture puede no aportar evidencia, debe declarar evidencia insuficiente, nunca probar inexistencia universal.

Campos opcionales ausentes tienen field_sources vacío; su ausencia se verifica en el parent raw, sin inventar un pointer resoluble. Snapshots RPC incluidos requieren evidencia de relectura canónica por número. Finality safe/finalized sólo se acepta si hay lectura del tag correspondiente que respalda el mismo hash/número; fixtures M0 sólo soportan unknown.

Fee de ejecución = gasUsed × effectiveGasPrice. Blob fee = blobGasUsed × blobGasPrice cuando ambos existen; total conocido para tipos Ethereum 0/1/2 con execution fee y sin indicadores de fees extra; tipo 3 requiere las dos componentes. Tipos nuevos o campos fee adicionales desconocidos→total null y advertencia. No calcular maxFeePerGas × gasUsed como fee real ni usar gasPrice como sustituto silencioso. Derivaciones citan campos receipt y tipo transaction. Fee en revert puede existir. Contradicción de blob fields en tipos 0–2→total null. No son claims ni anomalías: la clasificación RULE-BASED de claims se aplicará en M7.

CLI offline: `node dist/normalize-cli.js fixture <id>`; usa manifest para conocer hash, FixtureAdapter y normalizador. Live explícito: `... live <tx-hash>` importa adapter dinámicamente sólo en esta rama. stdout JSON y stderr código seguro; no persistencia automática. Bundle se puede guardar mediante redirección del shell. Mantener el guard offline permitiendo sólo módulos locales/archivos/hash; no importar transporte RPC en modo fixture.

Pruebas: golden success/reverted/pending y tipos desconocidos, uint256 máximo, valor cero, creación, campos opcionales, fees execution/blob/unknown, logs raw, snapshots inconsistentes, citas inexistentes, tampering, IDs determinísticos, deep freeze y CLI offline. Golden esperado se mantiene en test, no en entrada del agente.
